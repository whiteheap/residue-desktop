# Agent guide

residue-ui is the residue Mac app: a Tauri 2 window over the residue CLI from [whiteheap/residue-cli](https://github.com/whiteheap/residue-cli), which it bundles. Rust in `src-tauri/`, React and TypeScript in `src/` (Kumo components, Phosphor icons, Tailwind 4). The [README](README.md) is the user contract. [CONTRIBUTING.md](CONTRIBUTING.md) has the build, the checks and the numbers to compare with.

The app lived in residue-cli's `app/` folder from residue-cli#40 to residue-cli#130, and the merges in #3 and #7 brought that history here. Issue and pull request numbers in those commits are residue-cli's. Cite them as `residue-cli#N`, in code and in docs, so they never read as this repository's.

## Invariants

These are why the app can be trusted with someone's worktrees. Do not weaken them without a decision recorded in [CHANGELOG.md](CHANGELOG.md).

- The app never reimplements a check, a verdict, a size or a deletion. Every action runs the residue binary bundled as the sidecar (`src-tauri/src/cli.rs`) with explicit arguments, stdin from `/dev/null` and a deadline, and reads its `--json` document. When residue gives no value, show residue's own words or an unavailable state, never a guess.
- Every child the app starts, residue or not, starts through `cli::spawn` (`cli::Run` calls it), one start at a time, so on macOS no child inherits another's pipes (residue-cli#116). `src-tauri/clippy.toml` refuses `Command::spawn`, `output` and `status` anywhere else.
- Removal is `residue remove --trash --json PATH...` (`src-tauri/src/lib.rs`, `remove`). The confirmation first shows residue's plan: the same command without `--yes`, which removes and purges nothing because stdin is not a terminal (exit status 3, each ready worktree skipped with verdict `candidate`). Nothing is removed without a click on the confirm: only that click runs it again with `--yes` and exactly the planned paths. It also passes `--as-of` with the shown plan's `generated_at`, taken from that plan's document, never from a new read, so residue judges every age at the plan's time and purges and forgets only what the plan could list (#13). `remove` checks that value's form (`AsOf`: RFC 3339 in UTC with whole seconds, as residue writes it) and refuses a confirm without one with kind `invalid`, running nothing; `--yes` never goes without it. Never `--no-trash`, never `--all`, never a scan root as a path.
- One confirmed removal runs at a time, also across a quit and a relaunch (#12). `remove` holds `Removals` (`src-tauri/src/removal.rs`) from before residue starts until it returns, and refuses another with kind `invalid`, running nothing. The app does not stop residue when it quits, so while residue runs, `removal-running.json` in the app's data directory (`~/Library/Application Support/com.whiteheap.residue/`) names its process by PID, start time and name, and a launch that finds it counts that removal as in flight until that process exits; one whose process has exited, or that the app cannot read, is removed. The window asks (`removal_running`) when it starts and when the removal dialog closes, and keeps Move to the trash off until `wait_for_removal` returns. Keep the refusal in `remove`: the window's guard alone does not hold, since an ask that fails turns Move to the trash on.
- A failure to draw stays in the part that failed: each screen and each dialog has its own `ErrorBoundary`. A dialog's boundary draws its panel in a dialog whose one way out is Close, which returns to the screen's fresh read: drawing the dialog again would start its flow again after its action may have run. The panel never says that nothing changed, since the result of a confirmed action may be what failed to draw.
- Restore runs only `residue restore --json ENTRY`, with a trash entry's or a removal record's `entry_path`. Listing runs `residue restore --json` in each folder and shows both `trash` and `removed`. A record's row says before the click what restore does not bring back (its `not_kept` ignored entries) and offers Restore only for a state it knows restore takes: `removed`, `interrupted` and `back` (Git lists the worktree at its path again; restore gives it what it lacks of the record). None for a record residue cannot read (`error`, `incomplete`), one it cannot tell is back (`unknown`, with `back_error`), or a state a newer residue adds.
- Automatic cleanup runs `residue service install`, `uninstall` and `status` (`src-tauri/src/service.rs`), and `launchctl print` of the service, which only reads, to show the job launchd holds when it is not what the agent file says (`launchd_job`). Never a `launchctl` that changes anything. It installs from a residue the user installed that is at least as new as the bundled one, or else from the app's own copy in `~/Library/Application Support/com.whiteheap.residue/bin/`, never from the binary inside the app bundle: the service records the binary's path, and the app can move or be deleted. Each service command reads the bundled residue's version again (`bundled_version_now`): an app replaced on disk while it runs has another release at the same path, so only the window's version line keeps the first read. A save writes the app's own copy only when the new copy prints the version its dialog showed (`copy_sidecar`), and keeps the copy it replaces under a second name until residue has written the agent file: when residue writes nothing, the old copy goes back (`Previous`), so a save that installs nothing leaves the service on the residue it ran.
- What the window says the service does comes from the service's arguments and the version of the binary it runs (`service.rs`, `watch_settings`), never from the bundled residue: `brew upgrade` changes the service's binary without the app. residue's defaults for options a service does not set are the `DEFAULT_*` constants in `service.rs` (`DEFAULT_KEEP_REMOVED` is residue-cli's `cli::DEFAULT_KEEP_REMOVED`), and `FETCH_SINCE` is the first release that fetches. `FETCH_PRUNES_LOCAL_UNTIL` in `src/lib/watch.ts` is the last release whose fetch can also delete a tag, note or other ref that a fetch refspec or `pruneTags` covers and the remote does not have, even one never pushed, and the window says so beside a fetch of that release or an older one (`fetchCaveat`). Copy that says how long removal records last names the service's `--keep-removed` when it sets one, else that default, and says which. Saving folders passes every one of the service's options on as written, including an option the app does not know, such as one a newer residue adds (`parse_watch`: it takes the next argument as its value unless that is an option or an absolute path). Never drop an option on a save. An argument that is neither an option nor a folder blocks the save (`Plan.blocked`), never a fall back to defaults. The preview is the saved service's pass: `watch --once --dry-run` with every option a save keeps, by the binary a save installs with, so it fetches when the service would. A save installs what its dialog showed or nothing: the dialog plans from its own read, made when it opens, and sends that read's `Basis` back (the binary a save installs with and its version, the options it keeps, and the running service's binary, version, folders and `--dry-run`, and the `fingerprint:` line of `residue service status`); `install` reads again and, when any of it differs, installs nothing and returns what changed (`Save::Changed`). It then passes that fingerprint as `residue service install --expect`, so residue compares the service with it once more right before it writes, under the lock every `service install` and `uninstall` takes, and exit 4 (`EXPECT_CHANGED`) is a `Save::Changed` too, with nothing written (#11). `status` runs with the binary a save installs with, or with the bundled one when that is the app's own copy (`installs_as`), since the fingerprint names the residue release that read it. A read with no fingerprint saves nothing. Never plan a save from the screen's read, never drop a field from the basis, and never install without `--expect`. One save or turn-off runs at a time: `install` and `uninstall` hold `Changes` for their whole run and refuse while another runs, and the window keeps its screen while one runs (`go` in `src/App.tsx`, `changingService`). While Preview or Save runs, the dialog's folders and mode stay as they were at the click (`locked`), so the preview it shows and the save it runs are of the folders it shows. Other text about residue's behavior states what the bundled residue-cli release does.
- The app bundles exactly one residue-cli release: the one `sidecar.lock` pins, by its version and the sha256 of its two macOS archives. It is `Contents/MacOS/residue-cli`: the app's own executable is `residue` (the Cargo `[[bin]]`), the name macOS shows, so a lookup of the CLI never takes `residue` beside the app, and a PATH search skips the app's own executable (`find_installer`). `scripts/sidecar.sh` downloads the two archives, checks each sha256 and its build-provenance attestation, checks each binary inside against the sha256 `sidecar.lock` pins for it, and joins the two with `lipo`. It refuses any file git tracks in `src-tauri/binaries/`, in every mode, and `--require-attestation`, which CI and the release run, downloads and checks again whatever is placed. `scripts/check-app.sh` fails a build whose residue-cli is not that release, by its version, the attestation check and each architecture's UUID. Never commit a binary, and never let CI or a release bundle a residue built from a checkout (`RESIDUE_CLI_SOURCE`).
- Two versions, each with one owner: the app's is `version` in `src-tauri/tauri.conf.json`, the bundled CLI's is `version` in `sidecar.lock`. `package.json` and `src-tauri/Cargo.toml` hold none. The window shows both. Moving `sidecar.lock` to another release is a pull request of its own: set its archive and binary checksums as the file says, read that release's CHANGELOG entry in residue-cli, and update the `DEFAULT_*` constants, `FETCH_SINCE`, `src/lib/types.ts` and any text about residue's behavior that it changes.
- Charts draw residue's numbers and shares of them, nothing else: `src/lib/viz.ts` turns residue's documents into shapes and `src/components/viz/` draws them. Emphasis is their one visual variable (`Tone`: bright, gray, hatched, rest), never a hue, and in forced colors each tone keeps a fill, an outline or the hatch. Every chart has a text equivalent on its screen (its caption, its legend's values, the list or the table), and nothing is reachable only through a chart. Never draw a count-down such as "days left": residue deletes a trash entry at the first removal or automatic cleanup in its repository after `--keep-trash`, not on a date.
- The window shows only the app's own pages and calls only the app's commands. `navigation_guard` in `src-tauri/src/lib.rs` refuses a navigation to any other page (`own_page`). Each command `run` registers is also in `src-tauri/commands.rs`, which `build.rs` gives an `allow-` permission, and `capabilities/default.json` grants it by name: a command missing from either is refused at its first call. The CSP refuses plugins, a `<base>`, form submissions and framing, the opener plugin opens no link a page clicks, and the dev server listens on `127.0.0.1` alone, the address `devUrl` names.
- Development aids stay out of release builds: `devshot.rs` compiles only for macOS debug builds, and the service preview (`DevPreview`) checks `cfg!(debug_assertions)`.

## Text

Text for a person, on every screen and in every dialog, is brief: a heading of a few words, a sentence or two under it, one line per result, each caveat beside its action, and detail one step away, in a disclosure or the README. Brief never drops a warning or a limit, and keeps residue's terms: candidate, keep, unknown. A button names its action and its object ("Move 3 to the trash", "Turn off automatic cleanup"), never "OK". A rule few readers need before they act, such as when a removal record is forgotten, goes in a disclosure.

## Cost

CPU and memory belong to the user, and the window stays open beside their editor, their builds and their coding agents. Measure a change to a hot path, or one that adds a dependency, a thread, a child process or a timer, before and after: both builds interleaved on one Mac, three runs or more each, every run in the pull request, system CPU apart from user CPU. Measure memory as `footprint -p PID` of the app, its WebContent and its GPU process, and CPU as `ps -o utime=,stime= -p PID`, user and system, before and after a fixed task (residue-cli#90). A change that makes a number worse says why it is worth it. [CONTRIBUTING.md](CONTRIBUTING.md#performance) has the numbers to compare with. File an issue for a slow or heavy component you find, in the app, a library or a tool it runs, with the measurement and the command that repeats it, before there is a fix.

- Tailwind scans only `src/` and the chunks of the Kumo components the app draws, listed in `src/styles.css`. Importing another Kumo component adds its chunk there, or it renders unstyled. `pnpm build` fails until the list names every Kumo component chunk in the bundle, and none it no longer holds (`bundle.ts`, `kumoSources`, residue-cli#124).
- The build keeps only Phosphor's regular, bold and fill weights (`bundle.ts`, `phosphorWeights`, residue-cli#123). It fails when the app's source or the Kumo code it bundles uses another weight, a weight it cannot read, or an `IconContext` value it cannot read, since that icon would render blank. To draw another weight, add it to `KEPT`.
- What follows the pointer is written to its element, not to state: a render of the Worktrees map draws every tile.
- residue's JSON reaches the window as the text residue printed (`cli::Document`). The app reads only its `schema`.

## Verify a change

On a machine that runs residue's service, its user's data and service are not test fixtures:

- Never run `residue service install` or `uninstall`, `--dry-run` and a scratch `HOME` included. launchd acts on the real login session (`gui/UID`) and the label `com.whiteheap.residue.watch` is shared, so either one replaces or removes that user's service. Run the app with `RESIDUE_APP_DEV_SERVICE=preview` to exercise the switch: it runs only `residue watch --once --dry-run`, which removes no worktree, and fetches as the service does unless the service sets `--no-fetch`. `residue service status` only reads.
- Remove and restore only in scratch repositories you create in a temporary folder. A scan of real folders only reads, and is fine for a realistic overview.
- To see the UI from a terminal that cannot record the screen, run `pnpm tauri dev` with `RESIDUE_APP_DEV_SNAPSHOT_DIR=DIR` and write a name into `DIR/request` ([CONTRIBUTING.md](CONTRIBUTING.md#development-builds)).

Then run what CI runs ([CONTRIBUTING.md](CONTRIBUTING.md#checks)). A change to the CLI the app bundles is a change to `sidecar.lock`, checked as the invariants above say.

A change to how the app moves worktrees to the trash (`src/views/RemoveDialog.tsx`, and its wiring and `watchRemoval` in `src/App.tsx`, `chosen` and the action bar's move button in `src/views/Worktrees.tsx`, the move button in `src/views/Detail.tsx`, `remove`, `removal_running` and `wait_for_removal` in `src-tauri/src/lib.rs`, `src-tauri/src/removal.rs`) or saves or turns off automatic cleanup (its dialogs in `src/views/Automatic.tsx`, `go` in `src/App.tsx`, `changingService` in `src/lib/api.ts`, `Basis`, `read`, `plan`, `install`, `uninstall` and `Changes` in `src-tauri/src/service.rs`) also runs `bash .agents/skills/verify-confirm-flows/check.sh`, about seven minutes. It model-checks every order of your clicks, residue's replies and changes outside the app in those flows, and fails when a rule breaks that did not before. It reads the models, not the code: update the model in the same change, as [its skill](.agents/skills/verify-confirm-flows/SKILL.md) says. `.github/workflows/model.yml` runs it when a model changes; it is not a required check.

## Release

The app's version is `version` in `src-tauri/tauri.conf.json`, not residue-cli's. To release X.Y.Z:

1. On a branch, set that `version` to X.Y.Z, and turn `## Unreleased` in `CHANGELOG.md` into a `## X.Y.Z (date)` section. The release notes come from that section, so it opens with what a user gets. Open a pull request: changing `tauri.conf.json` starts the release workflow's dry run, which builds and checks the DMG and prints the notes. Squash merge it.
2. Tag the merge commit on `main`: `git fetch origin`, check that `origin/main` is that commit, then `git tag -s vX.Y.Z -m "residue-ui X.Y.Z" origin/main` and `git push origin vX.Y.Z`.
3. `.github/workflows/release.yml` fails unless the tag matches the version. It places the residue-cli release `sidecar.lock` pins with its attestation checked, builds the universal app, and checks the app inside the DMG with `scripts/check-app.sh` and a launch. Then it publishes `residue-macos.dmg` with `SHA256SUMS`, a build-provenance attestation, and notes that name the residue-cli release inside. It also fails unless the tagged commit is on `main`. Check the published DMG with `gh attestation verify residue-macos.dmg --repo whiteheap/residue-ui --deny-self-hosted-runners --cert-identity https://github.com/whiteheap/residue-ui/.github/workflows/release.yml@refs/tags/vX.Y.Z`, which accepts only that workflow at that tag.

A pull request that changes the workflow, `scripts/`, `sidecar.lock` or `tauri.conf.json`, and `gh workflow run release.yml --ref BRANCH`, are dry runs that attest and publish nothing.
